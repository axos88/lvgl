<Callout type="info" title="v9.6 will be the last v9 release">
  LVGL v9.6 is the final release in the v9 series. All symbols marked
  `LV_DEPRECATED` are removed in v10.0.
</Callout>

## Configuration

Starting with v9.6, LVGL's configuration was overhauled. [Kconfig](https://github.com/lvgl/lvgl/blob/master/Kconfig)
is now the **single source of truth** for every configuration option. The files
you actually use, `lv_conf_template.h` (the file you copy to `lv_conf.h`), the
internal headers that apply defaults, and the `CONFIG_*` bridge, are all
*generated* from the Kconfig tree, so the three ways of configuring LVGL
(`lv_conf.h`, Kconfig, and compiler `-D` defines) can no longer drift apart.

<Callout type="info" title="lv_conf.h is not going away">
  Configuring LVGL with a hand-written `lv_conf.h` is still **fully supported**
  and remains the default for most projects. Kconfig being the source of truth
  is an internal change: `lv_conf_template.h` is now generated from it, but you
  copy and edit it exactly as before.
</Callout>

### `lv_conf_template.h` overhaul

`lv_conf_template.h` is now generated from Kconfig rather than hand-maintained.
The practical effects when you upgrade:

- Options now appear in a consistent order with consistent comments, and every
  option's default matches the `Kconfig` default exactly.
- A few options were renamed or restructured (see below). Old names still work
  for now, they produce warnings or errors at compile time but they will be
  **removed in v10.0**, so update them.

The simplest way to migrate an existing `lv_conf.h` is to copy the new
`lv_conf_template.h` over a fresh `lv_conf.h` and re-apply your changes, or to
re-run `scripts/generate_lv_conf.py` if you're using `lv_conf.defaults`. Either way,
watch the compiler output for the deprecation `#warning`s listed below.

### Minimal configuration

The `LV_CONF_MINIMAL` switch, which disabled all widgets, themes, layouts and
fonts in one go, has been **removed**. A one-off switch like this doesn't fit a
Kconfig-driven model, where presets are expressed as *defconfigs*. The minimal
preset now lives at `configs/defconfigs/empty.defconfig`:

```bash
# Build LVGL from the empty preset
cmake -B build -DLV_BUILD_USE_KCONFIG=ON -DLV_BUILD_DEFCONFIG_PATH=configs/defconfigs/empty.defconfig
```

If you set `LV_CONF_MINIMAL` (in `lv_conf.h` or Kconfig) you'll get a build
warning. Start from the "empty" defconfig and re-enable only what you need.

### Renamed and restructured options

Every old name below **still compiles** for now: it emits a `#warning` at build
time and continues to work (it is mapped to its replacement, or still honored in
place), and is **removed in v10.0**.

Watch your build log after upgrading and update each one the warning/error points at.

#### Color format

`LV_COLOR_DEPTH` is replaced by `LV_COLOR_FORMAT_DEFAULT`, which names the format
you want directly instead of describing how many bits it takes.

The reasoning is that a bit count is ambiguous: `LV_COLOR_DEPTH 16` means either
`RGB565` or `RGB565_SWAPPED`, and `32` means either `XRGB8888` or `ARGB8888`

This new configuration makes the choice explicit:

| Before | After |
|---|---|
| `LV_COLOR_DEPTH 1` | `LV_COLOR_FORMAT_DEFAULT LV_COLOR_FORMAT_I1` |
| `LV_COLOR_DEPTH 8` | `LV_COLOR_FORMAT_DEFAULT LV_COLOR_FORMAT_L8` |
| `LV_COLOR_DEPTH 16` | `LV_COLOR_FORMAT_DEFAULT LV_COLOR_FORMAT_RGB565` |
| `LV_COLOR_DEPTH 24` | `LV_COLOR_FORMAT_DEFAULT LV_COLOR_FORMAT_RGB888` |
| `LV_COLOR_DEPTH 32` | `LV_COLOR_FORMAT_DEFAULT LV_COLOR_FORMAT_XRGB8888` |

Beyond those five, `LV_COLOR_FORMAT_DEFAULT` also accepts formats that no
`LV_COLOR_DEPTH` value could reach:

- `LV_COLOR_FORMAT_RGB565_SWAPPED`: big-endian RGB565 panels, previously handled
  by swapping bytes in the flush callback
- `LV_COLOR_FORMAT_ARGB8888` — a screen with a real alpha channel
- `LV_COLOR_FORMAT_ARGB8888_PREMULTIPLIED` — premultiplied alpha, what compositors
  such as Wayland expect

`LV_COLOR_DEPTH` is still defined and still readable from your own code
(`#if LV_COLOR_DEPTH == 32` keeps working), but it is now **derived** from
`LV_COLOR_FORMAT_DEFAULT` rather than something you set, and it no longer appears
in `lv_conf_template.h`. Being a bit count it is lossy: both RGB565 formats report
`16`, and all three 8888 formats report `32`.

`LV_COLOR_FORMAT_NATIVE` and `LV_COLOR_FORMAT_NATIVE_WITH_ALPHA` were
`lv_color_format_t` enumerators picked by `LV_COLOR_DEPTH`. They are no longer part of
the enum and live on as compatibility macros in `lv_api_map_v9_5.h`, so they keep
working unless you build with `LV_DISABLE_API_MAPPING`. `NATIVE` is a plain alias of
`LV_COLOR_FORMAT_DEFAULT`; `NATIVE_WITH_ALPHA` maps each format to its alpha-capable
companion, unchanged from v9.5 for the five formats a color depth could select:

| `LV_COLOR_FORMAT_DEFAULT` | `LV_COLOR_FORMAT_NATIVE_WITH_ALPHA` |
|---|---|
| `I1` | `I1` (there is no alpha-capable 1-bit format) |
| `L8` | `AL88` |
| `RGB565`, `RGB565_SWAPPED` | `RGB565A8` |
| `RGB888`, `XRGB8888`, `ARGB8888` | `ARGB8888` |
| `ARGB8888_PREMULTIPLIED` | `ARGB8888_PREMULTIPLIED` |

In new code name the format you want explicitly (`LV_COLOR_FORMAT_ARGB8888` in most
cases), or read a display's actual format with `lv_display_get_color_format()`.

<Callout type="info" title="Kconfig configs migrate themselves">
  The deprecated color depth choice is still there, and the default color format is
  seeded from it: an existing `.config` or `defconfig` holding
  `CONFIG_LV_COLOR_DEPTH_32=y` selects `XRGB8888` with no change on your side.
  Replace it with `CONFIG_LV_COLOR_FORMAT_XRGB8888=y`
 </Callout>

<Callout type="tip">
`LV_COLOR_FORMAT_DEFAULT` sets the format each display *starts* with, not a global
constant. Any display's format can be changed at runtime with
<ApiLink name="lv_display_set_color_format" display="lv_display_set_color_format(display, LV_COLOR_FORMAT_...)" />,
and two displays can run different formats. This needs support from the driver:
its flush callback has to handle the pixel layout it is handed, and the draw
buffer(s) must be large enough for the new format.
</Callout>

#### Memory

| Removed | Replacement |
|---|---|
| `LV_MEM_SIZE_KILOBYTES` | `LV_MEM_SIZE` (value in **bytes**) |
| `LV_MEM_POOL_EXPAND_SIZE_KILOBYTES` | `LV_MEM_SIZE` (set the full size in **bytes**) |
| `LV_MEM_POOL_EXPAND_SIZE` | `LV_MEM_SIZE` (set the full pool size) |

```c
/* Before */
#define LV_MEM_SIZE_KILOBYTES 64
/* After */
#define LV_MEM_SIZE (64 * 1024)
```

#### Threading

| Removed | Replacement |
|---|---|
| `LV_DRAW_THREAD_STACKSIZE` | `LV_DRAW_THREAD_STACK_SIZE` |

#### LZ4 / ThorVG

`LZ4` and `ThorVG` no longer have separate `_INTERNAL`/`_EXTERNAL` enables.
Instead, enable the library itself with `LV_USE_LZ4` / `LV_USE_THORVG`,
and use the `_INTERNAL` flag to choose between the bundled source and an externally provided one:

| Removed | Replacement |
|---|---|
| `LV_USE_LZ4_EXTERNAL` | `LV_USE_LZ4` = 1 and `LV_USE_LZ4_INTERNAL` = 0 |
| `LV_USE_THORVG_EXTERNAL` | `LV_USE_THORVG` = 1 and `LV_USE_THORVG_INTERNAL` = 0 |

<Callout type="warning">
    If your project previously had `LV_USE_THORVG_INTERNAL` enabled (with no `LV_USE_THORVG_EXTERNAL`), you must now also enable `LV_USE_THORVG`.
    Leaving `LV_USE_THORVG` disabled while `LV_USE_THORVG_INTERNAL` is enabled will result in a build error.
    The same applies to `LV_USE_LZ4` and `LV_USE_LZ4_INTERNAL`.
</Callout>

#### GPU (VG-Lite)

The VG-Lite GPU is now chosen with a single `LV_VG_LITE_GPU` option instead of a free-form series/revision pair.
Set it to one of the predefined GPU/revision combinations:

| Removed | Replacement |
|---|---|
| `LV_VG_LITE_HAL_GPU_SERIES` | `LV_VG_LITE_GPU` |
| `LV_VG_LITE_HAL_GPU_REVISION` | `LV_VG_LITE_GPU` |

`LV_VG_LITE_GPU` accepts one of the following values:

| Value | GPU | Revision |
|---|---|---|
| `LV_VG_LITE_GPU_GC255_0X40A` | GC255 | 0x40A |
| `LV_VG_LITE_GPU_GC355_0X0_1215` | GC355 | 0x0_1215 |
| `LV_VG_LITE_GPU_GC355_0X0_1216` | GC355 | 0x0_1216 |
| `LV_VG_LITE_GPU_GC555_0X423` | GC555 | 0x423 |
| `LV_VG_LITE_GPU_GC555_0X423_ECO` | GC555 | 0x423 ECO |
| `LV_VG_LITE_GPU_GCNANOULTRAV_0X1003` | GCNanoUltraV | 0x1003 |

#### Drivers

No driver infers its rendering backend from the enabled draw units any more. SDL and DRM now expose an explicit `LV_<DRIVER>_BACKEND` choice; Wayland instead lets you
enable each of its backends individually and resolves between them at runtime. See below.

Their `LV_<DRIVER>_AUTO_BACKEND` flags (enabled by default) exist purely to ease migration: they let LVGL reproduce the old auto-detected backend so existing projects
don't silently switch to a different backend on update simply because they never set one explicitly. Leaving an `_AUTO_BACKEND` flag enabled triggers a build-time warning.
These flags are not meant to be relied on going forward and will be removed for v10, every project should set its backend explicitly with `LV_<DRIVER>_BACKEND` and then
disable the corresponding `_AUTO_BACKEND` flag to silence the warning.

- **SDL** — while `LV_SDL_AUTO_BACKEND` is enabled, the backend is inferred the legacy way: EGL when `LV_USE_OPENGLES` and (`LV_USE_DRAW_NANOVG` or `LV_USE_DRAW_OPENGLES`) are enabled,
otherwise Textures when `LV_USE_DRAW_SDL` is enabled, otherwise Software. Set `LV_SDL_AUTO_BACKEND` to 0 and select a backend explicitly with `LV_SDL_BACKEND`:

  | Value | Backend |
  |---|---|
  | `LV_SDL_BACKEND_SW` | Software (SDL surface) |
  | `LV_SDL_BACKEND_TEXTURE` | Cached SDL textures (enable: `LV_USE_DRAW_SDL`) |
  | `LV_SDL_BACKEND_EGL` | EGL (OpenGL ES, hardware-accelerated; requires `LV_USE_DRAW_OPENGLES` or `LV_USE_DRAW_NANOVG`) |

  On Kconfig's side, buffer count is now a single integer instead of two separate flags:

  | Removed | Replacement |
  |---|---|
  | `LV_SDL_SINGLE_BUFFER` | `LV_SDL_BUF_COUNT` = 1 |
  | `LV_SDL_DOUBLE_BUFFER` | `LV_SDL_BUF_COUNT` = 2 |

- **Linux DRM** — while `LV_LINUX_DRM_AUTO_BACKEND` is enabled, the backend is inferred the legacy way: EGL when `LV_USE_OPENGLES` is enabled, otherwise FBDEV.
Set `LV_LINUX_DRM_AUTO_BACKEND` to 0 and select a backend explicitly with `LV_LINUX_DRM_BACKEND`:

  | Value | Backend |
  |---|---|
  | `LV_LINUX_DRM_BACKEND_FBDEV` | Dumb buffers (no GPU) |
  | `LV_LINUX_DRM_BACKEND_GBM` | GBM DMA buffers |
  | `LV_LINUX_DRM_BACKEND_EGL` | EGL (OpenGL ES, hardware-accelerated; enable: `LV_USE_OPENGLES`) |

  `LV_USE_LINUX_DRM_GBM_BUFFERS` is no longer a user-facing setting. It is now set internally and automatically enabled whenever the `EGL` or `GBM` backend is selected; it should no longer be set directly in `lv_conf.h`.

- **Wayland** — the backend is no longer inferred, and no longer has to be a single one.

  Previously `LV_WAYLAND_USE_SHM`, `LV_WAYLAND_USE_EGL` and `LV_WAYLAND_USE_G2D` were derived internally and mutually exclusive: enabling `LV_USE_OPENGLES` gave you EGL,
  otherwise enabling `LV_USE_G2D` gave you G2D, otherwise you got SHM. Setting them in `lv_conf.h` had no effect.

  They are now ordinary options that you set yourself, and **more than one may be enabled at a time**:

  | Symbol | Backend | Default |
  |---|---|---|
  | `LV_WAYLAND_USE_SHM` | SHM (Shared Memory) | on, except with a GPU draw unit |
  | `LV_WAYLAND_USE_EGL` | EGL (OpenGL ES, hardware-accelerated; enable: `LV_USE_OPENGLES`) | off; under Kconfig, on with a GPU draw unit |
  | `LV_WAYLAND_USE_G2D` | G2D (NXP i.MX hardware accelerator; enable: `LV_USE_DRAW_G2D`) | off |

  There is also a new fourth backend, `LV_WAYLAND_USE_DMABUF`, which presents software-rendered frames as linear DMA-BUFs.
  See the [Wayland driver docs](/integration/embedded_linux/drivers/wayland#dma-buf).

  To reproduce exactly what you had before, enable the one backend the old rules would have picked for your config. `LV_USE_G2D` no longer plays a part in the choice:
  it is a deprecated no-op (see [No-op options kept for compatibility](#no-op-options-kept-for-compatibility)) and the G2D backend is now tied to `LV_USE_DRAW_G2D`.

  | You had | Backend you got | Add |
  |---|---|---|
  | `LV_USE_OPENGLES` = 1 | EGL | `LV_WAYLAND_USE_EGL` = 1 (keep `LV_USE_OPENGLES`) |
  | `LV_USE_G2D` = 1 | G2D | `LV_WAYLAND_USE_G2D` = 1 and `LV_USE_DRAW_G2D` = 1 |
  | neither | SHM | nothing — `LV_WAYLAND_USE_SHM` is on by default |

  See the [Wayland driver docs](/integration/embedded_linux/drivers/wayland#runtime-backend-selection) for more information.

- **X11** — render mode (unrelated to backend selection) is now a single value mapped onto the standard `LV_DISPLAY_RENDER_MODE_*` constants:

  | Removed | Replacement |
  |---|---|
  | `LV_X11_RENDER_MODE_PARTIAL` | `LV_X11_RENDER_MODE` = `LV_DISPLAY_RENDER_MODE_PARTIAL` |
  | `LV_X11_RENDER_MODE_DIRECT` | `LV_X11_RENDER_MODE` = `LV_DISPLAY_RENDER_MODE_DIRECT` |
  | `LV_X11_RENDER_MODE_FULL` | `LV_X11_RENDER_MODE` = `LV_DISPLAY_RENDER_MODE_FULL` |

#### Calendar day/month names

The two array macros became individual short strings, so each name is now a plain
Kconfig-settable string and you can localize one without redefining the whole
array. `LV_CALENDAR_WEEK_STARTS_MONDAY` is unchanged, ordering is handled
internally. The old array macros still work (with a `#warning`).

| Removed | Replacement |
|---|---|
| `LV_CALENDAR_DEFAULT_DAY_NAMES` | `LV_MONDAY_STR` ... `LV_SUNDAY_STR` |
| `LV_CALENDAR_DEFAULT_MONTH_NAMES` | `LV_JANUARY_STR` ... `LV_DECEMBER_STR` |

#### libinput XKB keymap

The single keymap struct became individual string options (again, so Kconfig can
set each one). The old struct macro still works (with a `#warning`):

| Removed | Replacement |
|---|---|
| `LV_LIBINPUT_XKB_KEY_MAP` | `LV_LIBINPUT_XKB_RULES`, `LV_LIBINPUT_XKB_MODEL`, `LV_LIBINPUT_XKB_LAYOUT`, `LV_LIBINPUT_XKB_VARIANT`, `LV_LIBINPUT_XKB_OPTIONS` |

```c
/* Before */
#define LV_LIBINPUT_XKB_KEY_MAP { .rules = NULL, .model = "pc101", .layout = "us", .variant = NULL, .options = NULL }

/* After */
#define LV_LIBINPUT_XKB_MODEL  "pc101"
#define LV_LIBINPUT_XKB_LAYOUT "us"
/* rules / variant / options default to "" */
```

### Macros that can't be set from Kconfig

Some configuration values are function-like or expression macros — for example
`LV_FONT_CUSTOM_DECLARE`, the custom `LV_ASSERT_HANDLER`, the `LV_ATTRIBUTE_*`
hooks, and NemaGFX pool attributes. Kconfig only stores booleans, integers and
strings, so it cannot hold these.

**If you configure with `lv_conf.h`, nothing changes** — keep defining these
macros inline exactly as before. `LV_FONT_CUSTOM_DECLARE`, `LV_ASSERT_HANDLER`,
the attribute hooks, etc. are all still honored when defined in `lv_conf.h`.

**If you configure with Kconfig**, you can't write such a macro as a Kconfig
value, so each module now offers a `LV_<MODULE>_USE_CUSTOM_INCLUDE` switch plus a
`LV_<MODULE>_CUSTOM_INCLUDE` path. Point it at a small header that defines the
macros, e.g.:

```c
/* my_lvgl_extra.h, referenced by LV_FONT_CUSTOM_INCLUDE */
#define LV_FONT_CUSTOM_DECLARE  LV_FONT_DECLARE(my_font_24)
#define LV_FONT_DEFAULT         &my_font_24
```

This pair exists for `FONT`, `ASSERT`, `ATTRIBUTE`, `SYSMON`, `NEMA` and the
global custom include. As part of unifying this convention, a couple of old
include/enable names were renamed (each still works with a `#warning`):

| Removed | Replacement |
|---|---|
| `LV_ASSERT_HANDLER_INCLUDE` | `LV_ASSERT_CUSTOM_INCLUDE` (enable with `LV_ASSERT_USE_CUSTOM_INCLUDE`) |

If you still rely on the old `LV_ASSERT_HANDLER_INCLUDE` and can't migrate
immediately, you can silence the deprecation warning with
`LV_DISABLE_ASSERT_HANDLER_INCLUDE_WARNING`. This only suppresses the
compiler warning, `LV_ASSERT_HANDLER_INCLUDE` itself still works the same
way. New projects should use `LV_ASSERT_CUSTOM_INCLUDE` and define their
custom assertion handler directly instead.

A related effect: `lv_conf_template.h` no longer prints an empty stub for every
overridable macro (`LV_ATTRIBUTE_*`, `LV_PROFILER_*`, `LV_EXPORT_CONST_INT`,
`LV_ASSERT_HANDLER`, ...). They are **not removed** — define them in `lv_conf.h`
or via a `*_CUSTOM_INCLUDE` and LVGL still picks them up; they just default to
empty/no-op otherwise.

### No-op options kept for compatibility

`LV_USE_PXP` and `LV_USE_G2D` never enabled drawing on their own, you always
also needed `LV_USE_DRAW_PXP` / `LV_USE_DRAW_G2D`. They are kept as **deprecated
no-ops** (and excluded from the generated headers) purely so existing
`defconfig`s that set `CONFIG_LV_USE_PXP` / `CONFIG_LV_USE_G2D` keep loading.
They have no effect and emit no warning. Use the real switches:

| No-op | Real switch |
|---|---|
| `LV_USE_PXP` | `LV_USE_DRAW_PXP` |
| `LV_USE_G2D` | `LV_USE_DRAW_G2D` |

See [Configuring LVGL](/integration/configuration) for the full picture of how
configuration works now.

## Core

### Argument checking

LVGL v9.6 standardizes public-API argument validation. `LV_ASSERT_OBJ` is
replaced by <ApiLink name="LV_CHECK_OBJ" />, which logs a warning and lets the
caller recover gracefully instead of halting the program.

```c
/* Before */
LV_ASSERT_OBJ(obj, &lv_label_class);
/* After */
LV_CHECK_OBJ(obj, &lv_label_class, return);
```

#### What `LV_CHECK_OBJ` actually checks

The macro is layered — each layer is independently configurable in `lv_conf.h`:

| Layer | Guard | What it checks |
|---|---|---|
| Base | `LV_USE_CHECK_ARG` | Enables the whole system; when 0 all three macros expand to nothing. Also enables NULL checks on all arguments regardless of whether Class or Validity guards are set. |
| Class | `LV_USE_CHECK_OBJ_CLASSTYPE` | `lv_obj_has_class(obj, cls)` — verifies the object is the expected widget type. |
| Validity | `LV_USE_CHECK_OBJ_VALIDITY` | `lv_obj_is_in_widget_tree(obj)` — verifies the object is still part of the live widget tree. |

All three layers default to `0` (disabled). Enable them selectively:

```c
/* lv_conf.h */
#define LV_USE_CHECK_ARG           1   /* master switch */
#define LV_USE_CHECK_OBJ_CLASSTYPE 1   /* also check class type */
#define LV_USE_CHECK_OBJ_VALIDITY  1   /* also check widget-tree membership */
```

When `LV_USE_CHECK_OBJ_CLASSTYPE` is `0`, `LV_CHECK_OBJ` still performs a
NULL check; when `LV_USE_CHECK_OBJ_VALIDITY` is `0`, it still performs the
class check (if enabled). The checks are cumulative.

<Callout type="warning" title="Enable only during development">
  `lv_obj_is_in_widget_tree()` walks the widget tree and `lv_obj_has_class()` traverses
  the class hierarchy — both add non-trivial overhead on every call site.
  Leave `LV_USE_CHECK_OBJ_CLASSTYPE` and `LV_USE_CHECK_OBJ_VALIDITY` at `0`
  in production builds.
</Callout>

#### Failure behavior

Two further options control what happens when a check fails:

```c
/* lv_conf.h */

/* Also call LV_ASSERT_HANDLER (halts / breakpoints like the old assert). */
#define LV_CHECK_ARG_ASSERT_ON_FAIL  0

/* How much to log when a check fails (requires LV_USE_LOG = 1). */
/* LV_CHECK_ARG_LOG_MODE_NONE    (0) – no output                               */
/* LV_CHECK_ARG_LOG_MODE_MINIMAL (1) – "Check failed" + file/line              */
/* LV_CHECK_ARG_LOG_MODE_VERBOSE (2) – "Check failed: <cond>" + caller message */
#define LV_CHECK_ARG_LOG_MODE  LV_CHECK_ARG_LOG_MODE_VERBOSE
```

Setting `LV_CHECK_ARG_ASSERT_ON_FAIL 1` restores the hard-abort behavior of
`LV_ASSERT_OBJ`, which can be useful during a debugging session.
`LV_CHECK_ARG_LOG_MODE` has no effect when `LV_USE_LOG` is `0`.

See the [Argument Checking](contributing/assertions/#argument-checking) docs for
the full <ApiLink name="LV_CHECK_ARG" /> and <ApiLink name="LV_CHECK_OBJ" /> API
if you need finer control.

### Assertions

Assertions in LVGL are now disabled by default and can be enabled with <ApiLink name="LV_USE_ASSERT"/>.

Note that these assertions are not required and should be disabled to improve performance when deploying your LVGL application.

### lv_obj

- `lv_obj_find_by_id()` is deprecated, use `lv_obj_find_by_name()` instead:
  ```c
  /* Before */
  lv_obj_t * obj = lv_obj_find_by_id(parent, my_id);

  /* After */
  lv_obj_t * obj = lv_obj_find_by_name(parent, "my_widget");
  ```

- The generic flag API — `lv_obj_add_flag()`, `lv_obj_remove_flag()`,
  `lv_obj_set_flag()`, `lv_obj_has_flag()` and `lv_obj_has_flag_any()` — is
  deprecated. Each flag now has a dedicated setter (`lv_obj_set_<flag>(obj, en)`)
  and getter (`lv_obj_is_<flag>(obj)`):
  ```c
  /* Before */
  lv_obj_add_flag(obj, LV_OBJ_FLAG_HIDDEN);
  lv_obj_remove_flag(obj, LV_OBJ_FLAG_CLICKABLE);
  lv_obj_set_flag(obj, LV_OBJ_FLAG_SCROLLABLE, en);
  bool h = lv_obj_has_flag(obj, LV_OBJ_FLAG_HIDDEN);

  /* After */
  lv_obj_set_hidden(obj, true);
  lv_obj_set_clickable(obj, false);
  lv_obj_set_scrollable(obj, en);
  bool h = lv_obj_is_hidden(obj);
  ```
  The custom-bit flags (`LV_OBJ_FLAG_USER_1`–`4`) can be accessed via
  `lv_obj_set/get_user_flag()`, which take a bit from 0 to 3 e.g `lv_obj_set_user_flag(obj, 0, true)`
  instead of lv_obj_get/set-flag(obj, LV_OBJ_FLAG_USER_1).

  A migration script is available at `scripts/migration/migrate_obj_flags.py`:
  ```bash
  	python3 scripts/migration/migrate_obj_flags.py path/to/your/project
  ```
  _Note: Only raw flag constants can be converted automatically. Expressions using variables will be skipped for safety._

## Observer

### Subject create/delete

The `lv_subject_init_<type>()` family and <ApiLink name="lv_subject_deinit"/> are
deprecated. A Subject is now allocated by LVGL with
<ApiLink name="lv_subject_create"/>, which takes the type and returns a pointer, and
freed with <ApiLink name="lv_subject_delete"/>. Every Subject is tracked by LVGL, so
any Subject still alive at `lv_deinit()` is deleted automatically.

Keep the returned pointer where the `lv_subject_t` value used to live, and drop the
`&` from every call that took its address:

```c
/* Before */
static lv_subject_t temperature;
lv_subject_init_int(&temperature, 20);
lv_label_bind_text(label, &temperature, "%d °C");
lv_subject_deinit(&temperature);

/* After */
static lv_subject_t * temperature;
temperature = lv_subject_create(LV_SUBJECT_TYPE_INT);
lv_subject_set_int(temperature, 20);
lv_label_bind_text(label, temperature, "%d °C");
lv_subject_delete(temperature);
```

The type is one of `LV_SUBJECT_TYPE_INT`, `LV_SUBJECT_TYPE_FLOAT`,
`LV_SUBJECT_TYPE_STRING`, `LV_SUBJECT_TYPE_POINTER`, `LV_SUBJECT_TYPE_COLOR` or
`LV_SUBJECT_TYPE_GROUP`.

There is no initial value parameter any more. `lv_subject_create()` starts the Subject
from a neutral value — `0` for int and float, `NULL` for pointer, black for color, an
empty string for string — and the initial value is set with
the regular `lv_subject_set_...()` function. Two consequences to keep in mind:

- After the first `lv_subject_set_...()` the previous value is the neutral one, not the
  initial one. `lv_subject_init_...()` set both to the initial value.
- A Subject no longer has a built-in range. Attach a clamping mapper instead, and
  attach it *before* the first value. See [Subject range removed](#subject-range-removed).

The string buffer moved out of the init call into its own setter. It takes the memory
as-is, so it still has to out-live the Subject:

```c
/* Before */
static lv_subject_t title;
lv_subject_init_string(&title, buf, sizeof(buf), "Hello");

/* After */
static lv_subject_t * title;
title = lv_subject_create(LV_SUBJECT_TYPE_STRING);
lv_subject_set_string_buffer_static(title, buf, sizeof(buf));
lv_subject_copy_string(title, "Hello");
```

### Deleting a Subject others depend on is refused

`lv_subject_delete()` now refuses if another Subject's mapper reads the one being
deleted, because that would leave the mapper without an input:

```c
lv_subject_delete(width);
/* -> LV_LOG_WARN("Subject is a dependency of 1 other Subject(s)...") and nothing happens */
```

Delete the dependents first, or take the whole derived chain down at once with
`lv_subject_delete_cascade()`, which works like SQL's `ON DELETE CASCADE`:

```c
lv_subject_delete_cascade(width);   /* deletes `area` and anything derived from it */
```

Subjects still alive at `lv_deinit()` are torn down regardless of their dependencies,
so application shutdown needs no ordering.

Deleting a Subject removes it from the dependency graph in both directions, so no
dangling edge is ever left behind.

### Mappers replace ad-hoc derived values

Every Subject can now have a **mapper**: one callback that owns the Subject's value.
The value slot is state, and the mapper is the only thing that writes it.

- `lv_subject_set_<type>()` seeds the slot with the value you wrote, then runs the mapper.
- When a dependency changes, the same mapper runs again on whatever the slot holds.

Which of the two roles a mapper plays is decided by its own code, not by a flag:

```c
/* Bounds what was written, so it transforms the input. */
static bool clamp_mapper(lv_subject_t * subject, void * user_data, int32_t input, int32_t * value)
{
    LV_UNUSED(subject);
    LV_UNUSED(user_data);
    int32_t before = *value;                       /* the previous stored value */
    *value = lv_subject_clamp_int(input, 0, 100);
    return *value != before;
}

/* Overwrites the slot from other Subjects, so it is a derived value. */
static bool sum_mapper(lv_subject_t * subject, void * user_data, int32_t input, int32_t * value)
{
    LV_UNUSED(subject);
    LV_UNUSED(user_data);
    LV_UNUSED(input);
    int32_t next = lv_subject_get_int(width) + lv_subject_get_int(height);
    if(next == *value) return false;
    *value = next;
    return true;
}
```

A mapper receives four things: the `subject`, its `user_data`, the `input` most recently
written, and `value`, an in/out pointer to the stored value that still holds the
**previous** one on entry.

Four things to know:

1. **The mapper does change detection.** It returns `true` only when it actually changed
   the stored value. `*value` holds the previous one when the mapper starts, so keeping a
   copy of it is all that is needed — which is why a Subject no longer stores any history.
2. **Dependencies wire themselves.** Every `lv_subject_get_...()` call made from inside a
   mapper registers the Subject it read as a dependency. The list is rebuilt on each run,
   so a mapper may read different Subjects on different runs. Nothing has to be declared.
3. **`user_data` is the mapper's captured state.** It is how a mapper reaches the
   Subjects and configuration it needs without them being file-scope globals, the way a
   closure captures variables. One mapper function can serve any number of Subjects.
4. **A mapper must not write a Subject.** A write from inside a mapper is ignored and
   logs a warning. Mappers read; side effects belong in an Observer of an
   `LV_SUBJECT_MODE_EAGER` Subject. Writing to a *derived* Subject from outside a mapper
   is also a no-op, silently, because the mapper overwrites what was written.

Each type has its own setter, so no casting is involved: `lv_subject_set_int_mapper()`,
`lv_subject_set_float_mapper()`, `lv_subject_set_pointer_mapper()`,
`lv_subject_set_color_mapper()`, `lv_subject_set_string_mapper()` and
`lv_subject_set_none_mapper()`. A string mapper is handed the Subject's buffer rather
than a value, because a string Subject owns its storage.

Pass the Subject's own configuration through `lv_subject_set_user_data()` and read it
back with `lv_subject_get_user_data()`. That is what makes one mapper function
reusable across several Subjects.

There is deliberately no `computed()` and no `effect()`. A mapper plus the mode below
covers both.

### Subject range removed

`lv_subject_set_min_value_int()`, `lv_subject_set_max_value_int()`,
`lv_subject_set_min_value_float()` and `lv_subject_set_max_value_float()` are
**removed**, together with the `min_value` and `max_value` fields. A clamping mapper
replaces them:

```c
/* Before */
subject = lv_subject_create(LV_SUBJECT_TYPE_INT);
lv_subject_set_min_value_int(subject, 0);
lv_subject_set_max_value_int(subject, 100);
lv_subject_set_int(subject, 50);

/* After */
static bool clamp_0_100(lv_subject_t * subject, void * user_data, int32_t input, int32_t * value)
{
    LV_UNUSED(subject);
    LV_UNUSED(user_data);
    int32_t before = *value;
    *value = lv_subject_clamp_int(input, 0, 100);
    return *value != before;
}

subject = lv_subject_create(LV_SUBJECT_TYPE_INT);
lv_subject_set_int_mapper(subject, clamp_0_100, NULL);
lv_subject_set_int(subject, 50);
```

The behavior is the same as before: the clamp applies to writes, so a two-way bound
Widget still round-trips through clamped values.

A mapper is more capable than the two fields were, because the limits can themselves
be Subjects:

```c
static bool clamp_reactive(lv_subject_t * subject, void * user_data, int32_t input, int32_t * value)
{
    LV_UNUSED(subject);
    LV_UNUSED(user_data);
    int32_t before = *value;
    *value = lv_subject_clamp_int(input, lv_subject_get_int(lower), lv_subject_get_int(upper));
    return *value != before;
}
```

Raising `lower` or lowering `upper` re-clamps, which the old fields could not do. And
because the mapper is handed the last *input* rather than the stored value, widening a
limit restores a value that had been clamped away, instead of leaving it stuck at the
old bound.

<Callout type="warning">
`lv_obj_add_subject_increment_event()` used to intersect its own range with the
Subject's `min_value`/`max_value` and use the narrower of the two. It now uses only
the range set with `lv_obj_set_subject_increment_event_min_value()` and
`..._max_value()`. If you relied on the Subject's range to bound an increment event,
either set the range on the event or add a clamping mapper to the Subject; a mapper
applies on top of whatever the event writes.
</Callout>

### Eager and lazy Subjects

A Subject with a mapper re-evaluates either eagerly or lazily.

| Mode | When the mapper runs | Purity |
|------|----------------------|--------|
| `LV_SUBJECT_MODE_LAZY` (default) | when the value is read, when an eager dependent pulls it, or at the next flush | must be **pure** |
| `LV_SUBJECT_MODE_EAGER` | inside the `lv_subject_set_...()` call that dirtied it | may have side effects |

A lazy Subject is only marked dirty when a dependency changes, so several writes in a
row collapse into one evaluation, and a Subject nothing ever reads is never computed at
all. An eager Subject recomputes immediately, which makes it the place for a side
effect.

Evaluation is glitch-free. A write first marks the whole dependent graph dirty, then
evaluates the eager Subjects, whose mappers pull their dependencies. In a diamond
(`A→B`, `A→C`, `B+C→D`) the sink `D` evaluates exactly once and never sees a fresh `B`
next to a stale `C`.

### The previous value is gone

`lv_subject_get_previous_int()`, `..._float()`, `..._string()`, `..._pointer()` and
`..._color()` are **removed**, along with the `prev_value` field, and
`lv_subject_set_string_buffer_static()` / `lv_subject_init_string()` lost their
`prev_buf` parameter — a string Subject needs only one buffer now.

Nothing is lost for change detection, which is what the previous value was mostly used
for: a mapper is handed the previous stored value in `*value`, so it can keep a copy and
compare. A Subject with no mapper compares the input against the stored value directly.

If an Observer genuinely needs the previous value — to animate away what was there
before, say — it remembers it itself:

```c
/* Before */
static void cb(lv_observer_t * observer, lv_subject_t * subject)
{
    int32_t prev = lv_subject_get_previous_int(subject);
    int32_t cur = lv_subject_get_int(subject);
    ...
}

/* After */
static void cb(lv_observer_t * observer, lv_subject_t * subject)
{
    static int32_t prev = 0;
    int32_t cur = lv_subject_get_int(subject);
    ...
    prev = cur;
}
```

Often the previous value turns out not to be needed at all. `lv_example_observer_4`
used it to un-check the previously selected button; deriving the state from the current
value only is both shorter and correct without any history.

### The caller decides who owns a pointer value

A pointer Subject stores a bare pointer, so somebody has to answer for the memory behind
it, and **the caller decides per write**:

```c
lv_subject_set_pointer(cfg, &config);                     /* borrowed, never released */
lv_subject_set_pointer_owned(frame, decode(), lv_free);   /* owned, released on replace */
```

An owned value is released once the Subject no longer refers to it, and whatever it still
owns is released when it is deleted. The two forms mix freely on the same Subject: each
pointer is released, or not, according to the write that introduced it.

A borrowed value has to stay valid **until a new value is written**, not just until the
call returns. A Subject keeps two references to it — the value it stores and the input it
retains for a re-evaluation — and a mapper is handed the retained input again every time
a dependency changes.

Two details worth knowing:

- Republishing the **same** pointer never releases it, so a driver that mutates its
  buffer in place and publishes it again is safe.
- The release happens **after** the mapper has run, so a mapper may still read the
  outgoing value, and ownership follows what the write handed in: a pointer the mapper
  came up with on its own is treated as borrowed.

String Subjects get the same pair. With a buffer they copy, as before, and
`lv_subject_copy_string()` has no lifetime question at all. Without a buffer they store a
`char *`, and `lv_subject_set_string()` / `lv_subject_set_string_owned()` say who owns it.

### String buffers became general buffers, and can grow

`lv_subject_set_buffer()` replaces the string-only buffer setup and works for pointer
Subjects too:

```c
/* Before */
lv_subject_set_string_buffer_static(title, buf, prev_buf, sizeof(buf));

/* After: a fixed buffer */
lv_subject_set_buffer(title, buf, sizeof(buf), NULL, NULL);

/* Or a growable one */
lv_subject_set_buffer(title, NULL, 0, my_realloc, my_free);
```

`lv_subject_set_string_buffer_static(subject, buf, size)` is kept as a convenience for
the fixed case, minus the `prev_buf` parameter that went with the previous value.

`realloc_cb` grows the buffer; `free_cb` releases it when it is replaced or the Subject is
deleted. Passing NULL for both gives the old fixed-footprint behaviour.

<Callout type="warning">
**A write that does not fit is now refused rather than truncated.** Previously
`lv_subject_copy_string()` clipped a long string to the buffer size. Now a fixed buffer
that is too small, or a `realloc_cb` that returns NULL, fails the write: the Subject keeps
its previous value and nobody is notified.

`lv_subject_copy_string()` and `lv_subject_snprintf()` therefore return `bool`. Ignoring
it still compiles, so this is a silent behaviour change for code that relied on clipping
— check it if you wrote strings that could overflow the buffer.
</Callout>

**If you relied on clipping, `lv_subject_copy_string_trimmed()` is the direct
replacement.** It grows the buffer if it can and stores as much as fits if it cannot, so
it behaves as the old `lv_subject_copy_string()` did for a fixed buffer:

```c
/* Before, which clipped silently */
lv_subject_copy_string(title, name);

/* After, same effect, and now explicit about it */
lv_subject_copy_string_trimmed(title, name);
```

Prefer it for anything the user reads, and keep the strict `lv_subject_copy_string()` for
values where a truncated result would be wrong rather than merely shortened. Change
detection is on the text that was stored, so two long strings that trim to the same thing
notify once.

`lv_subject_snprintf()` measures the result first, so a growable buffer grows to fit
instead of truncating.

### Pointer Subjects can copy their value

`lv_subject_copy_pointer(subject, data, size)` is a third way for a pointer Subject to
hold its value, next to borrowing and owning it, and the one with no lifetime question:

```c
static uint8_t storage[sizeof(sample_t)];
lv_subject_set_buffer(samples, storage, sizeof(storage), NULL, NULL);

lv_subject_copy_pointer(samples, &sample, sizeof(sample));
lv_subject_get_pointer_size(samples);   /* how many bytes were stored */
```

Copying also gives proper change detection, because the previous bytes are compared
against the new ones. A driver that republishes a mutated buffer then notifies only when
something actually moved — which otherwise needs a mapper keeping a last-known-good copy.

A Subject either copies or refers: setting a buffer makes the borrowing and owning
setters refuse, and the copying functions need a buffer.

### An Observer has one pointer for application data

`lv_subject_add_observer_with_target()` and `lv_observer_get_target()` are **removed**.
An Observer used to carry two general-purpose pointers, `target` and `user_data`, which
did the same job; now there is one:

```c
/* Before */
lv_subject_add_observer_with_target(subject, cb, my_data, NULL);
my_data_t * d = lv_observer_get_target(observer);

/* After */
lv_subject_add_observer(subject, cb, my_data);
my_data_t * d = lv_observer_get_user_data(observer);
```

The Widget slot stays, because it is not data:
`lv_subject_add_observer_obj(subject, cb, obj, user_data)` still takes both, and the
Widget is a **lifetime link** — deleting it deletes the Observer. An Observer bound to a
Widget therefore still has its own `user_data`, which is what several of LVGL's own
bindings rely on: they keep a descriptor in `user_data` and the Widget separately.

`lv_observer_get_target_obj()` is unchanged and now simply returns that Widget. If you
were using `lv_observer_get_target()` to get a Widget, switch to it:

```c
/* Before */
lv_obj_t * label = lv_observer_get_target(observer);

/* After */
lv_obj_t * label = lv_observer_get_target_obj(observer);
```

### Releasing what you attached to a Subject

`lv_subject_set_delete_cb()` registers a callback that runs just before a Subject is
destroyed, on `lv_subject_delete()`, `lv_subject_delete_cascade()` and the automatic
teardown in `lv_deinit()`. Use it to release anything the application attached — a
mapper's `user_data`, a handle, a registration elsewhere:

```c
static void free_config(lv_subject_t * subject, void * user_data)
{
    LV_UNUSED(subject);
    lv_free(user_data);
}

lv_subject_set_int_mapper(bounded, clamp_mapper, cfg);
lv_subject_set_delete_cb(bounded, free_config, cfg);
```

For the common case of a mapper's `user_data` being a plain `lv_malloc()` allocation,
`lv_subject_set_mapper_user_data_owned()` says it in one call and needs no callback:

```c
lv_subject_set_int_mapper(bounded, clamp_mapper, lv_malloc(sizeof(range_t)));
lv_subject_set_mapper_user_data_owned(bounded);
```

This is what makes it practical to hand a mapper allocated state rather than a static.
Note that `lv_subject_set_external_data()` also releases on deletion, but it is behind
`LV_USE_EXT_DATA`, which is off by default, and it is a separate slot from the mapper's
`user_data`.

### Immediate and batched Observers

An Observer's mode says **when it is notified**, and it is also what decides whether a
lazy Subject is dragged into evaluating eagerly.

| Mode | When the Observer is notified |
|------|-------------------------------|
| `LV_OBSERVER_MODE_IMMEDIATE` (default) | inside the `lv_subject_set_...()` call that changed the value, exactly as in v9 |
| `LV_OBSERVER_MODE_BATCHED` | once per `lv_subject_flush()`, i.e. once per frame, however many times the value changed |

An immediate Observer makes a lazy Subject act eager for as long as it is subscribed.
A batched Observer does not. An eager Subject notifies *all* of its Observers, batched
ones included, as soon as it evaluates.

**Existing code needs no changes here.** A Subject defaults to lazy and an Observer
defaults to immediate, so `lv_subject_add_observer()` promotes the Subject and
`lv_subject_set_int()` notifies synchronously, exactly as before.

`LV_OBSERVER_MODE_BATCHED` is the equivalent of a scheduled effect. Use it when an
Observer only needs the latest value:

```c
lv_observer_t * observer = lv_subject_add_observer(samples, refresh_chart_cb, NULL);
lv_observer_set_mode(observer, LV_OBSERVER_MODE_BATCHED);

/* 50 writes in one frame -> refresh_chart_cb runs once */
```

Promotion changes *when* a Subject's mapper runs, not what it may do. A lazy Subject's
mapper has to stay pure even while an immediate Observer promotes it.

### Setting a value no longer always maps or notifies

For an **eager** Subject nothing changed in kind: `lv_subject_set_...()` applies the
mapper and notifies before it returns.

For a **lazy** Subject — the default — a write records the input and stops there. The
mapper runs when something reads the Subject, when an eager dependent pulls it, or at
the next flush. Notification is deferred the same way.

```c
lv_subject_set_int(volume, 5);
lv_subject_set_int(volume, 6);
lv_subject_set_int(volume, 7);   /* nothing mapped, nobody notified */

lv_subject_get_int(volume);      /* the mapper runs once, here */
```

Two consequences worth knowing:

- **A getter is never stale.** Every `lv_subject_get_...()` brings the Subject up to date
  first, so reading always gives the mapped value. Only reaching into `subject->value`
  directly can see an un-mapped one, and that was never public API.
- **A lazy mapper must be pure**, and only ever sees the *last* value written. A mapper
  that accumulates or must see every value the Subject passes through has to be declared
  `LV_SUBJECT_MODE_EAGER`. This is why `lv_subject_create_min()` and
  `lv_subject_create_max()` are eager: a running extremum that only saw the values
  somebody happened to read would be wrong.

Deferral applies to the scalar input types. These always map on the spot regardless of
mode: one with an immediate Observer, which promotes it anyway; one that owns its value,
because ownership of an incoming pointer only transfers once the mapper stores it; and
one whose input is a pointer or a string, because such an input is borrowed — only valid
for the duration of the write, and the mapper may read through it rather than just
storing it.

If you relied on the old behaviour of reading `subject->value` straight after a write,
use the getter instead.

### A Subject can be written as one type and observed as another

`lv_subject_create_mapped(input_type, value_type)` creates a Subject whose
`lv_subject_set_...()` function is the one for `input_type` and whose
`lv_subject_get_...()` is the one for `value_type`. The mapper converts:

```c
lv_subject_t * level = lv_subject_create_mapped(LV_SUBJECT_TYPE_FLOAT, LV_SUBJECT_TYPE_INT);
lv_subject_set_int_mapper(level, level_mapper, NULL);

lv_subject_set_float(level, 72.5f);   /* written as a float */
lv_subject_get_int(level);            /* read as an enum value */
```

This is why a mapper's `input` is an `lv_subject_value_t` rather than a typed parameter:
one mapper family, selected by the value type, has to serve every input type. Read the
member matching the input type — `input.float_v` above. For an ordinary Subject the two
types are the same and `lv_subject_get_input_type()` returns the value type.

It collapses what would otherwise be a source plus a derived Subject into one, for the
case where the raw form is of no interest. Two Subjects are still the right answer when
the raw value is worth observing separately.

### Clamped Subjects take their bounds at run time

The Subject returned by `lv_subject_create_clamped()` is written with an
`lv_subject_range_t`, so its bounds can be changed while it runs:

```c
lv_subject_value_t lo = { .num = 1 };
lv_subject_value_t hi = { .num = 25 };
lv_subject_t * bounded = lv_subject_create_clamped(reading, lo, hi, NULL);

lv_subject_set_int(reading, 30);            /* bounded reports 25 */

lv_subject_range_t wider = { .min_value = { .num = 1 }, .max_value = { .num = 100 } };
lv_subject_set_pointer(bounded, &wider);    /* bounded reports 30 */

lv_subject_range_t higher = { .min_value = { .num = 50 }, .max_value = { .num = 100 } };
lv_subject_set_pointer(bounded, &higher);   /* bounded reports 50 */
```

Each write notifies, because the clamped value really changed. Widening the range brings
back the reading it had clamped away, because the bound is applied to the source's
current value rather than to what was stored. The range is copied out, so the struct does
not have to outlive the call.

### Observer mappers

An Observer can map the value on its way out, so a Subject of one type can drive a
Widget setter of another. This is what lets an integer Subject set a Label's text
without an intermediate string Subject:

```c
static bool int_to_text(lv_observer_t * observer, const char ** out)
{
    static char buf[32];  /* the mapper owns the storage */
    lv_subject_t * subject = lv_observer_get_subject(observer);
    char next[32];
    lv_snprintf(next, sizeof(next), "Value: %" LV_PRId32, lv_subject_get_int(subject));
    if(lv_strcmp(next, buf) == 0) return false;  /* unchanged: leave the Widget alone */
    lv_strlcpy(buf, next, sizeof(buf));
    *out = buf;
    return true;
}

lv_obj_bind_string_mapped(label, int_subject, lv_label_set_text, int_to_text);
```

The mapper is passed at bind time rather than set afterwards, because binding notifies
the Observer immediately. Use `lv_obj_bind_bool_mapped()`, `lv_obj_bind_int_mapped()`,
`lv_obj_bind_float_mapped()`, `lv_obj_bind_string_mapped()`,
`lv_obj_bind_color_mapped()` or `lv_obj_bind_pointer_mapped()`. Unlike the plain
`lv_obj_bind_...()` functions these place no type requirement on the Subject.

When the mapper returns `false` the Widget setter is not called at all.

Unlike a Subject's mapper, an Observer's mapper does **not** register dependencies. An
Observer is not a node in the dependency graph and runs only when its own Subject
notifies. If you need to react to several Subjects, make a derived Subject or an
`LV_SUBJECT_TYPE_NONE` aggregate.

### Forwarding a Subject to a setter that takes more arguments

`lv_obj_bind_int()` and friends only fit a setter shaped `void (lv_obj_t *, value)`.
Two additions cover the setters that take more.

For style properties — 129 setters, all `(obj, value, selector)`:

```c
lv_obj_bind_style_int(box, subject_pad, lv_obj_set_style_pad_all, LV_PART_MAIN);
lv_obj_bind_style_color(box, subject_col, lv_obj_set_style_bg_color, LV_PART_MAIN);
lv_obj_bind_style_opa(box, subject_opa, lv_obj_set_style_bg_opa, LV_PART_MAIN);
```

For anything else, a macro generates the bridging Observer callback at file scope:

```c
LV_SUBJECT_FORWARD_INT(set_slider, lv_slider_set_value, LV_ANIM_OFF)
...
lv_subject_add_observer_obj(subject_value, set_slider, slider, NULL);
```

Both replace hand-written Observer callbacks that existed only to unpack a Subject and
call a setter. Neither is required: a setter shaped exactly `(obj, value)` still works
with `lv_obj_bind_int()` / `lv_obj_bind_string()` and so on.

### Group Subjects removed

`LV_SUBJECT_TYPE_GROUP` is **removed**, together with `lv_subject_init_group()`,
`lv_subject_set_group_list_static()` and `lv_subject_get_group_element()`. A mapper
expresses the same thing and more, so the dedicated type no longer earns its place.

Use an `LV_SUBJECT_TYPE_NONE` Subject — one with no value of its own — and a mapper that
reads whatever it should react to. Reading them is what makes them dependencies:

```c
/* Before */
static lv_subject_t * list[4] = {hour, minute, format, am_pm};
time_subject = lv_subject_create(LV_SUBJECT_TYPE_GROUP);
lv_subject_set_group_list_static(time_subject, list, 4);

static void time_cb(lv_observer_t * observer, lv_subject_t * subject)
{
    int32_t h = lv_subject_get_int(lv_subject_get_group_element(subject, 0));
    int32_t m = lv_subject_get_int(lv_subject_get_group_element(subject, 1));
    ...
}

/* After */
static bool time_mapper(lv_subject_t * subject)
{
    LV_UNUSED(subject);
    (void)lv_subject_get_int(hour);
    (void)lv_subject_get_int(minute);
    (void)lv_subject_get_int(format);
    (void)lv_subject_get_int(am_pm);
    return true;                 /* notify whenever any of them changed */
}

time_subject = lv_subject_create(LV_SUBJECT_TYPE_NONE);
lv_subject_set_none_mapper(time_subject, time_mapper);

static void time_cb(lv_observer_t * observer, lv_subject_t * subject)
{
    int32_t h = lv_subject_get_int(hour);   /* read the sources directly */
    int32_t m = lv_subject_get_int(minute);
    ...
}
```

What you gain over a group:

- The member list is not a separate array you have to keep alive, so there is no stale
  pointer to leave behind when a member is deleted. The members are real dependencies,
  and `lv_subject_delete()` refuses to delete one while the aggregate reads it.
- The mapper decides *when* to notify. Returning `true` unconditionally reproduces a
  group's "notify on any change"; returning a condition gives you a threshold or filter:

  ```c
  static bool any_alarm(lv_subject_t * subject)
  {
      LV_UNUSED(subject);
      return lv_subject_get_int(temp) > 90 || lv_subject_get_int(pressure) > 200;
  }
  ```
- The members can be read conditionally, so the dependency set can change from run to run.

An `LV_SUBJECT_TYPE_NONE` Subject is `LV_SUBJECT_MODE_EAGER` by default, so its
Observers fire as soon as an input changes, as a group's did. Inspect the members with
`lv_subject_get_dependency_count()` and `lv_subject_get_dependency()`.

<Callout type="info">
`LV_SUBJECT_TYPE_NONE` also became creatable: `lv_subject_create()` used to refuse it.
The enum value `6` that `LV_SUBJECT_TYPE_GROUP` occupied is left unused so the other
type values keep their meaning.
</Callout>

### Ready-made derived Subjects

Two pairs of helpers cover the cases that used to need `min_value`/`max_value` or a
hand-written mapper.

**Running extremum.** `lv_subject_create_min()` and `lv_subject_create_max()` create a
Subject that records the smallest or largest value its source has passed through:

```c
lv_subject_t * lowest  = lv_subject_create_min(temperature, NULL);
lv_subject_t * highest = lv_subject_create_max(temperature, NULL);

lv_subject_set_int(temperature, 20);   /* lowest 20, highest 20 */
lv_subject_set_int(temperature, 25);   /* lowest 20, highest 25 */
lv_subject_set_int(temperature, 15);   /* lowest 15, highest 25 */
```

Pass `NULL` for the compare callback to use the natural ordering, which exists for
`LV_SUBJECT_TYPE_INT`, `LV_SUBJECT_TYPE_FLOAT` and `LV_SUBJECT_TYPE_COLOR`. A pointer
Subject has no natural ordering, so it needs one:

```c
static int cheaper(lv_subject_t * subject, lv_subject_value_t a, lv_subject_value_t b)
{
    LV_UNUSED(subject);
    const item_t * ia = a.pointer;
    const item_t * ib = b.pointer;
    return (ia->price > ib->price) - (ia->price < ib->price);
}

lv_subject_t * cheapest = lv_subject_create_min(offered_item, cheaper);
```

These are eager, so they record every value the source passes through rather than only
the ones somebody happened to read.

**Bounded mirror.** `lv_subject_create_clamped()` creates a Subject that follows its
source, bounded to a range. It takes the bounds and a compare callback, so it works for
any orderable type:

```c
lv_subject_value_t lo = { .num = 0 };
lv_subject_value_t hi = { .num = 100 };
lv_subject_t * bounded = lv_subject_create_clamped(raw, lo, hi, NULL);
lv_subject_set_int(raw, 150);          /* raw stays 150, bounded reports 100 */
```

`lv_subject_compare_int()`, `lv_subject_compare_float()` and
`lv_subject_compare_color()` are ready to pass as the callback, and
`lv_subject_clamp_int()` / `lv_subject_clamp_float()` help when writing a clamping
mapper by hand.

Note the difference from a clamping mapper: this bounds a *separate* Subject and leaves
the source alone. To bound a Subject in place — which is what `min_value`/`max_value`
did, and what keeps a two-way Widget binding round-tripping through clamped values —
give that Subject a clamping mapper instead.

Both kinds of helper own their configuration, so do not call
`lv_subject_set_user_data()` on the Subject they return.

### lv_obj_bind_flag_if_* / lv_obj_bind_state_if_*

- The `lv_obj_bind_flag_if_*` and `lv_obj_bind_state_if_*` families
  (`_eq`/`_not_eq`/`_gt`/`_ge`/`_lt`/`_le`) are deprecated. For a boolean subject,
  bind a widget flag with `lv_obj_bind_bool()` — the dedicated per-flag setters
  (`lv_obj_set_hidden()`, `lv_obj_set_clickable()`, …) can be passed directly as
  the callback. For a state, or for any comparison against a reference value, add
  a custom observer with `lv_subject_add_observer_obj()`:
  ```c
  /* Before: hide a widget while a 0/1 subject is non-zero */
  lv_obj_bind_flag_if_not_eq(obj, &subject, LV_OBJ_FLAG_HIDDEN, 0);

  /* After */
  lv_obj_bind_bool(obj, subject, lv_obj_set_hidden);

  /* Before: disable a widget while a subject is greater than 80 */
  lv_obj_bind_state_if_gt(obj, &subject, LV_STATE_DISABLED, 80);

  /* After */
  static void disabled_observer_cb(lv_observer_t * observer, lv_subject_t * subject)
  {
      lv_obj_t * obj = lv_observer_get_target_obj(observer);
      lv_obj_set_state(obj, LV_STATE_DISABLED, lv_subject_get_int(subject) > 80);
  }
  lv_subject_add_observer_obj(subject, disabled_observer_cb, obj, NULL);
  ```

## Widgets

### lv_qrcode

- No API change, but a behavioral one: `lv_qrcode_set_size()` and
  `lv_qrcode_set_quiet_zone()` now re-encode the QR code, and the colors are
  re-applied, when they are called *after* the data. Previously such a change was
  silently dropped and the widget kept showing the bitmap produced by
  `lv_qrcode_update()` / `lv_qrcode_set_data()`. The properties may now be set in
  any order.

  To make this possible the widget keeps a copy of the payload, which costs
  `data_len` bytes per QR code object.

- New: `lv_qrcode_set_update_mode(qr, LV_QRCODE_UPDATE_MODE_DEFERRED)` collapses
  several property changes into a single re-encode on the next redraw. The default,
  `LV_QRCODE_UPDATE_MODE_IMMEDIATE`, re-encodes inside the setter.

- New: `lv_qrcode_render()` re-encodes the stored payload without taking it as an
  argument, which is how property changes made in the deferred update mode are applied.

- New: `lv_qrcode_get_render_failed()` reports whether the last encode failed, for the
  re-encodes whose result cannot be returned (the void property setters, and the
  deferred re-encode done by the draw pass).
